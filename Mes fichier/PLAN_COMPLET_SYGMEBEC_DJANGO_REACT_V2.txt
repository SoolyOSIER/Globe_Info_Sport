1. DIAGRAMME DE CAS D'UTILISATION (Image 1 — SYGMEBEC)
───────────────────────────────────────────────────────

ACTEURS (avec hiérarchie par généralisation — héritage des droits) :

  Secretaire        → acteur de base
      ▲
      │ (hérite de)
  Pasteur           → hérite de TOUS les cas d'utilisation de Secretaire + les siens
      ▲
      │ (hérite de)
  Administrateur    → hérite de TOUS les cas d'utilisation de Pasteur + les siens

CAS D'UTILISATION PAR ACTEUR :

  SECRETAIRE :
    • Enregistrer un membre
    • Modifier un membre              «include» → Rechercher un membre
    • Changer statut
    • Creer un evenement
    • Modifier un evenement           «include» → Consulter un evenement
    • Generer rapport                 «include» → Consulter un evenement
                                       «include» → Rechercher un membre

  PASTEUR (en plus des droits de Secretaire) :
    • Supprimer un evenement          «include» → Consulter un evenement
    • Supprimer un membre             «include» → Rechercher un membre

  ADMINISTRATEUR (en plus des droits de Pasteur) :
    • Gerer les comptes utilisateurs

  CAS D'UTILISATION INCLUS (réutilisés, non accessibles directement) :
    • Rechercher un membre
    • Consulter un evenement

→ Cette hiérarchie sera traduite en back-end par un système de RÔLES CUMULATIFS
  (RoleAcces) et en front-end par des routes protégées imbriquées par niveau.

2. DIAGRAMME DE CLASSES (Image 2 — SYGMEBEC)
──────────────────────────────────────────────

  Utilisateur (Idenetifiant, motDePasse, DateCreationCompte, dernierAcces)
      ── 1 a un 1 ──► RoleAcces (nomRole)
      ── 0..1 correspond a 1 ──► Membre

  Membre (nom)
      ── 1 a un 1 ──► Statut (libelle)
      ── 1 est responsable de 0..* ──► Evenement (titre, date, lieu, description, dateCreation)
      ── 1 possede 0..* ──► HistoriqueStatut (ancienStatut, nouveauStatut, dateChangement)
      ── 0..* occupe 0..* ──► Fonction (nomFonction, dateDebut, dateFin)
      ── 1 contient 1 ──► Rapport (dateGeneration, titre, dateFin)

  Rapport
      ── 1 genere selon 1 ──► CritereFiltrage (statut, periode)

→ Tous les modèles Django ci-dessous respectent EXACTEMENT ces classes,
  attributs et cardinalités, en y ajoutant uniquement les champs techniques
  indispensables (id, timestamps, related_name) sans dénaturer le diagramme.

3. NOTE SUR L'AJOUT DU SITE VITRINE (extension hors diagrammes fournis)
─────────────────────────────────────────────────────────────────────────
Les diagrammes fournis (cas d'utilisation + classes) couvrent uniquement la
gestion INTERNE des membres/événements par le personnel de l'église
(Secrétaire, Pasteur, Administrateur). Ils ne modélisent pas la présence
PUBLIQUE de l'organisation sur le web.

La PARTIE IV de ce plan ajoute donc un périmètre complémentaire, cohérent
avec le métier mais non représenté dans les diagrammes UML d'origine :
un SITE VITRINE PUBLIC, consultable sans authentification, permettant aux
visiteurs de découvrir l'organisation, consulter les événements publics,
soumettre une demande d'adhésion en ligne, s'inscrire à un événement et
contacter l'église. Ces nouveaux besoins sont traduits par :
  • une nouvelle application Django "vitrine" (back-end, PARTIE IV.B) qui
    RÉUTILISE les modèles existants (Membre, Evenement, Statut) sans les
    modifier structurellement, et ajoute uniquement des modèles de
    "capture" (DemandeAdhesion, InscriptionEvenement, MessageContact,
    ImageGalerie) qui alimentent ensuite les modèles métier via validation
    humaine (le Secrétaire transforme une DemandeAdhesion en Membre) ;
  • un second projet front-end React ("gestmembres-vitrine", PARTIE IV.C
    à M), indépendant du back-office, déployé séparément, consommant
    uniquement les endpoints publics de la même API Django.

PARTIE I — ARCHITECTURE GÉNÉRALE
================================================================================

STACK TECHNIQUE
───────────────
  Back-End  : Django 4.2 + Django REST Framework + SimpleJWT
  Front-End : 2 SPA distinctes servies séparément
                1) React 18 + Vite (Back-Office / Admin)     — PARTIE III
                2) React 18 + Vite (Site Vitrine Public)      — PARTIE IV
              Router v6 + TanStack Query + Zustand (les deux projets)
  Base de données : PostgreSQL 15
  Cache           : Redis 7 (sessions/recherches + broker Celery)
  Tâches async    : Celery + django-celery-beat (rapports périodiques, emails)
  PDF             : ReportLab / WeasyPrint (génération des rapports)
  Emails          : SMTP (production) / console (dev)
  Documentation API : drf-spectacular (Swagger / OpenAPI)
  Anti-spam       : Honeypot + Google reCAPTCHA v3 + throttling DRF (site vitrine)
  CI/CD           : GitHub Actions
  Conteneurisation: Docker + docker-compose

RÔLES & PUBLICS
────────────────────────────────────────────────────────────────────────────
  Personnel interne (Back-Office, authentifié) — hiérarchie cumulative :
    SECRETAIRE      → Enregistrer/Modifier membres, Rechercher, Changer statut,
                       Créer/Modifier événements, Consulter événements,
                       Générer rapports, Valider les demandes d'adhésion en ligne
    PASTEUR         → Tous les droits de SECRETAIRE + Supprimer membre/événement
    ADMINISTRATEUR  → Tous les droits de PASTEUR + Gérer les comptes utilisateurs

  Public (Site Vitrine, anonyme ou membre authentifié léger) :
    VISITEUR ANONYME → Consulter le site, les événements publics, la galerie,
                        soumettre une demande d'adhésion, s'inscrire à un
                        événement, envoyer un message de contact
    MEMBRE CONNECTÉ   → (si Utilisateur lié à son Membre) accès à un espace
                        personnel : profil, historique de ses inscriptions

FLUX GÉNÉRAL
────────────
  React Back-Office (5173) ──HTTP/JSON──▶ Django API (8000) /api/v1/...
  React Vitrine      (5174) ──HTTP/JSON──▶ Django API (8000) /api/v1/public/...
  Django             ──▶ PostgreSQL (Membres, Événements, Rapports, Demandes…)
  Django             ──▶ Celery/Redis (rapports PDF, emails, notifications)
  Django             ──▶ SMTP (statuts, rapports, adhésions, contact)

  class RoleAcces(models.Model):
      """ Diagramme : RoleAcces (+nomRole) """
      nomRole = models.CharField(max_length=30, unique=True, choices=[
          ('SECRETAIRE', 'Secrétaire'),
          ('PASTEUR', 'Pasteur'),
          ('ADMINISTRATEUR', 'Administrateur'),
      ])

      def __str__(self):
          return self.nomRole

  class UtilisateurManager(BaseUserManager):
      def create_user(self, identifiant, password=None, **extra):
          user = self.model(identifiant=identifiant, **extra)
          user.set_password(password)        # motDePasse hashé (jamais en clair)
          user.save(using=self._db)
          return user

      def create_superuser(self, identifiant, password=None, **extra):
          extra.setdefault('is_staff', True)
          extra.setdefault('is_superuser', True)
          return self.create_user(identifiant, password, **extra)

  class Utilisateur(AbstractBaseUser, PermissionsMixin):
      """ Diagramme : Utilisateur (+Idenetifiant, +motDePasse,
                                    +DateCreationCompte, +dernierAcces) """
      identifiant         = models.CharField(max_length=150, unique=True)   # Idenetifiant
      # motDePasse est géré nativement par AbstractBaseUser (champ 'password', hashé)
      date_creation_compte = models.DateTimeField(auto_now_add=True)        # DateCreationCompte
      dernier_acces        = models.DateTimeField(null=True, blank=True)    # dernierAcces

      role_acces = models.ForeignKey(                  # 1 a un 1 RoleAcces
          RoleAcces, on_delete=models.PROTECT, related_name='utilisateurs')

      membre = models.OneToOneField(                   # 0..1 correspond a 1 Membre
          'members.Membre', on_delete=models.SET_NULL,
          null=True, blank=True, related_name='utilisateur')

      is_active = models.BooleanField(default=True)
      is_staff  = models.BooleanField(default=False)

      objects = UtilisateurManager()
      USERNAME_FIELD = 'identifiant'
      REQUIRED_FIELDS = []

      def __str__(self):
          return self.identifiant

  class Statut(models.Model):
      """ Diagramme : Statut (+libelle) """
      libelle = models.CharField(max_length=50, unique=True)
      # Exemples : Actif, Inactif, Suspendu, Visiteur, Nouveau converti

      def __str__(self):
          return self.libelle

  class Membre(TimeStampedModel):
      """ Diagramme : Membre (+nom) """
      nom = models.CharField(max_length=150)
      # Champs additionnels indispensables (non dénaturants, requis pour un vrai
      # système de gestion de membres) :
      prenom        = models.CharField(max_length=150, blank=True)
      telephone     = models.CharField(max_length=30, blank=True)
      email         = models.EmailField(blank=True)
      adresse       = models.CharField(max_length=255, blank=True)
      date_naissance = models.DateField(null=True, blank=True)
      date_adhesion  = models.DateField(auto_now_add=True)

      statut = models.ForeignKey(                      # 1 a un 1 Statut
          Statut, on_delete=models.PROTECT, related_name='membres')

      fonctions = models.ManyToManyField(               # 0..* occupe 0..*
          'Fonction', through='MembreFonction', related_name='membres')

      def __str__(self):
          return f"{self.nom} {self.prenom}"

  class HistoriqueStatut(models.Model):
      """ Diagramme : HistoriqueStatut (+ancienStatut, +nouveauStatut,
                                          +dateChangement) — 1 possede 0..* """
      membre         = models.ForeignKey(
          Membre, on_delete=models.CASCADE, related_name='historiques_statut')
      ancien_statut  = models.CharField(max_length=50)   # ancienStatut
      nouveau_statut = models.CharField(max_length=50)   # nouveauStatut
      date_changement = models.DateTimeField(auto_now_add=True)  # dateChangement
      modifie_par    = models.ForeignKey(
          'accounts.Utilisateur', on_delete=models.SET_NULL, null=True)

      class Meta:
          ordering = ['-date_changement']

  class Fonction(models.Model):
      """ Diagramme : Fonction (+nomFonction, +dateDebut, +dateFin)
                       — 0..* occupe 0..* avec Membre """
      nomFonction = models.CharField(max_length=100)
      dateDebut   = models.DateField()
      dateFin     = models.DateField(null=True, blank=True)

      def __str__(self):
          return self.nomFonction

  class MembreFonction(models.Model):
      """ Table pivot explicite de la relation M2M 'occupe' """
      membre   = models.ForeignKey(Membre, on_delete=models.CASCADE)
      fonction = models.ForeignKey(Fonction, on_delete=models.CASCADE)

      class Meta:
          unique_together = ('membre', 'fonction')

G. AUTHENTIFICATION JWT & SÉCURITÉ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STRATÉGIE JWT :
  • Access Token   : 15 minutes, envoyé dans le corps JSON
  • Refresh Token  : 7 jours, stocké en httpOnly cookie sécurisé
  • USERNAME_FIELD = 'identifiant' (correspond au champ "Idenetifiant" du diagramme)
  • Le même mécanisme JWT est réutilisé, en lecture restreinte, par l'espace
    membre du site vitrine (PARTIE IV.K) — un Membre ne peut se connecter que
    si son compte Utilisateur existe déjà et lui a été communiqué.

FLUX D'AUTHENTIFICATION :
  1. POST /auth/login/    { identifiant, password } → { access, user } + cookie refresh
  2. React stocke 'access' en mémoire (Zustand, jamais localStorage)
  3. Axios interceptor ajoute Authorization: Bearer <access>
  4. À expiration → POST /auth/token/refresh/ (cookie envoyé automatiquement)
  5. Mise à jour de dernier_acces à chaque login (signal post_save côté vue)

  class LoginView(TokenObtainPairView):
      def post(self, request, *args, **kwargs):
          response = super().post(request, *args, **kwargs)
          refresh = response.data.pop('refresh')
          response.set_cookie('refresh_token', refresh, httponly=True,
                               secure=True, samesite='Lax', max_age=7*24*3600)
          user = Utilisateur.objects.get(identifiant=request.data['identifiant'])
          user.dernier_acces = timezone.now()
          user.save(update_fields=['dernier_acces'])
          response.data['user'] = UtilisateurSerializer(user).data
          return response

  # Traduit fidèlement la généralisation du diagramme :
  # Administrateur ⊃ Pasteur ⊃ Secretaire

  HIERARCHIE = {'SECRETAIRE': 1, 'PASTEUR': 2, 'ADMINISTRATEUR': 3}

  class IsSecretaireOrPlus(BasePermission):
      def has_permission(self, request, view):
          role = request.user.role_acces.nomRole
          return HIERARCHIE.get(role, 0) >= HIERARCHIE['SECRETAIRE']

  class IsPasteurOrPlus(BasePermission):
      def has_permission(self, request, view):
          role = request.user.role_acces.nomRole
          return HIERARCHIE.get(role, 0) >= HIERARCHIE['PASTEUR']

  class IsAdministrateur(BasePermission):
      def has_permission(self, request, view):
          return request.user.role_acces.nomRole == 'ADMINISTRATEUR'

src/api/axiosClient.js :
  const api = axios.create({
      baseURL: import.meta.env.VITE_API_URL,
      withCredentials: true,          // pour le cookie refresh httpOnly
  });

  api.interceptors.request.use((config) => {
      const token = useAuthStore.getState().accessToken;
      if (token) config.headers.Authorization = `Bearer ${token}`;
      return config;
  });

  api.interceptors.response.use(
      (res) => res,
      async (error) => {
          if (error.response?.status === 401) {
              const { data } = await api.post('/auth/token/refresh/');
              useAuthStore.getState().setAccessToken(data.access);
              return api(error.config);   // relance la requête originale
          }
          return Promise.reject(error);
      }
  );

OBJECTIF :
  Donner à l'église une présence publique sur le web, indépendante du
  back-office, permettant à tout visiteur de :
    1. Découvrir l'organisation (mission, valeurs, équipe, historique)
    2. Consulter les événements publics à venir et passés
    3. S'inscrire en ligne à un événement
    4. Soumettre une demande d'adhésion en ligne
    5. Consulter une galerie photo
    6. Contacter l'église via un formulaire
    7. (si compte lié) se connecter à un espace membre pour consulter son
       profil et l'historique de ses inscriptions

PÉRIMÈTRE TECHNIQUE :
  • Projet front-end INDÉPENDANT ("gestmembres-vitrine"), build et déploiement
    séparés du back-office (domaines distincts, ex. www.sygmebec.org vs
    admin.sygmebec.org)
  • Consomme la MÊME API Django, sur des routes dédiées préfixées /public/
    (lecture/écriture anonyme, throttlées) et /membre/ (authentifié, lecture
    seule pour un Membre connecté)
  • Ne modifie AUCUN modèle du diagramme de classes fourni : les demandes
    publiques transitent par des modèles "tampon" (DemandeAdhesion,
    InscriptionEvenement, MessageContact) validés manuellement par le
    personnel (Secrétaire+) avant de devenir des données métier définitives
    (ex. Membre)

PRINCIPE DE VALIDATION HUMAINE (garde-fou métier) :
  Visiteur → DemandeAdhesion (statut EN_ATTENTE)
           → Secrétaire consulte /demandes-adhesion (back-office, PARTIE III.F)
           → Secrétaire clique "Valider" → crée un Membre réel (Statut =
             "Nouveau converti" par défaut) + DemandeAdhesion.statut = VALIDEE
           → ou "Rejeter" → DemandeAdhesion.statut = REJETEE (avec motif)

  class DemandeAdhesion(TimeStampedModel):
      """ Formulaire public d'adhésion — alimente Membre après validation """
      nom            = models.CharField(max_length=150)
      prenom         = models.CharField(max_length=150)
      email          = models.EmailField()
      telephone      = models.CharField(max_length=30, blank=True)
      dateNaissance  = models.DateField(null=True, blank=True)
      message        = models.TextField(blank=True)
      dateDemande    = models.DateTimeField(auto_now_add=True)
      statut         = models.CharField(max_length=20, default='EN_ATTENTE',
                          choices=[('EN_ATTENTE', 'En attente'),
                                   ('VALIDEE', 'Validée'),
                                   ('REJETEE', 'Rejetée')])
      motif_rejet    = models.CharField(max_length=255, blank=True)
      membre_cree    = models.OneToOneField(
          'members.Membre', on_delete=models.SET_NULL,
          null=True, blank=True, related_name='demande_origine')
      traite_par     = models.ForeignKey(
          'accounts.Utilisateur', on_delete=models.SET_NULL, null=True, blank=True)

      def __str__(self):
          return f"{self.nom} {self.prenom} ({self.statut})"

  class InscriptionEvenement(TimeStampedModel):
      """ Inscription publique à un événement (avec ou sans compte) """
      evenement   = models.ForeignKey(
          'events.Evenement', on_delete=models.CASCADE, related_name='inscriptions')
      nom         = models.CharField(max_length=150)
      prenom      = models.CharField(max_length=150)
      email       = models.EmailField()
      telephone   = models.CharField(max_length=30, blank=True)
      nombrePlaces = models.PositiveIntegerField(default=1)
      dateInscription = models.DateTimeField(auto_now_add=True)
      membre      = models.ForeignKey(                  # rempli si visiteur connecté
          'members.Membre', on_delete=models.SET_NULL, null=True, blank=True)

      class Meta:
          ordering = ['-dateInscription']

  class MessageContact(TimeStampedModel):
      """ Formulaire de contact public """
      nom      = models.CharField(max_length=150)
      email    = models.EmailField()
      sujet    = models.CharField(max_length=200)
      message  = models.TextField()
      dateEnvoi = models.DateTimeField(auto_now_add=True)
      traite   = models.BooleanField(default=False)

  class ImageGalerie(TimeStampedModel):
      """ Photo affichée sur la page Galerie du site vitrine """
      titre      = models.CharField(max_length=150, blank=True)
      image      = models.ImageField(upload_to='galerie/')
      evenement  = models.ForeignKey(
          'events.Evenement', on_delete=models.SET_NULL, null=True, blank=True,
          related_name='photos')
      ordre      = models.PositiveIntegerField(default=0)
      dateAjout  = models.DateTimeField(auto_now_add=True)

      class Meta:
          ordering = ['ordre', '-dateAjout']

  class EvenementPublicSerializer(ModelSerializer):
      """ Champs limités — pas de données internes (responsable interne,
          historique, etc.) """
      places_restantes = SerializerMethodField()
      class Meta:
          model = Evenement
          fields = ['id', 'titre', 'date', 'lieu', 'description', 'image',
                     'capacite', 'places_restantes']

      def get_places_restantes(self, obj):
          if obj.capacite is None:
              return None
          inscrits = obj.inscriptions.aggregate(t=Sum('nombrePlaces'))['t'] or 0
          return max(obj.capacite - inscrits, 0)

  class DemandeAdhesionCreateSerializer(ModelSerializer):
      honeypot = CharField(required=False, allow_blank=True, write_only=True)
      class Meta:
          model = DemandeAdhesion
          fields = ['nom', 'prenom', 'email', 'telephone', 'dateNaissance',
                     'message', 'honeypot']

      def validate_honeypot(self, value):
          if value:                       # champ piège rempli → probable bot
              raise ValidationError("Requête invalide.")
          return value

  class InscriptionEvenementCreateSerializer(ModelSerializer):
      class Meta:
          model = InscriptionEvenement
          fields = ['evenement', 'nom', 'prenom', 'email', 'telephone', 'nombrePlaces']

      def validate(self, data):
          evenement = data['evenement']
          if evenement.capacite is not None:
              inscrits = evenement.inscriptions.aggregate(
                  t=Sum('nombrePlaces'))['t'] or 0
              if inscrits + data['nombrePlaces'] > evenement.capacite:
                  raise ValidationError("Plus assez de places disponibles.")
          return data

  class MessageContactCreateSerializer(ModelSerializer):
      class Meta:
          model = MessageContact
          fields = ['nom', 'email', 'sujet', 'message']

  class ImageGalerieSerializer(ModelSerializer):
      class Meta:
          model = ImageGalerie
          fields = ['id', 'titre', 'image', 'evenement', 'dateAjout']

  class EvenementPublicListView(ListAPIView):
      # GET /public/evenements/  — «Consulter un evenement» côté public
      queryset = Evenement.objects.filter(est_public=True).order_by('date')
      serializer_class = EvenementPublicSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public-read'
      filter_backends = [DjangoFilterBackend, SearchFilter, OrderingFilter]
      search_fields = ['titre', 'lieu', 'description']
      filterset_fields = ['lieu']

  class EvenementPublicDetailView(RetrieveAPIView):
      # GET /public/evenements/{id}/
      queryset = Evenement.objects.filter(est_public=True)
      serializer_class = EvenementPublicSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public-read'

  class InscriptionEvenementCreateView(CreateAPIView):
      # POST /public/evenements/{id}/inscription/
      serializer_class = InscriptionEvenementCreateSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public'

      def perform_create(self, serializer):
          inscription = serializer.save(evenement_id=self.kwargs['id'])
          send_inscription_confirmation.delay(inscription.id)  # Celery

  class DemandeAdhesionCreateView(CreateAPIView):
      # POST /public/adhesion/
      serializer_class = DemandeAdhesionCreateSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public'

      def perform_create(self, serializer):
          demande = serializer.save()
          notifier_nouvelle_demande_adhesion.delay(demande.id)  # Celery

  class MessageContactCreateView(CreateAPIView):
      # POST /public/contact/
      serializer_class = MessageContactCreateSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public'

      def perform_create(self, serializer):
          message = serializer.save()
          notifier_nouveau_message_contact.delay(message.id)   # Celery

  class ImageGalerieListView(ListAPIView):
      # GET /public/galerie/
      queryset = ImageGalerie.objects.all()
      serializer_class = ImageGalerieSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public-read'

  class MonProfilMembreView(RetrieveUpdateAPIView):
      # GET/PATCH /membre/mon-profil/  (Membre connecté uniquement)
      serializer_class = MembreDetailSerializer
      permission_classes = [IsAuthenticated]

      def get_object(self):
          if not self.request.user.membre_id:
              raise PermissionDenied("Aucun profil membre lié à ce compte.")
          return self.request.user.membre

  class MesInscriptionsListView(ListAPIView):
      # GET /membre/mes-inscriptions/  (Membre connecté uniquement)
      serializer_class = InscriptionEvenementCreateSerializer
      permission_classes = [IsAuthenticated]

      def get_queryset(self):
          return InscriptionEvenement.objects.filter(
              membre=self.request.user.membre)

B.6 PERMISSIONS, ANTI-SPAM ET RATE-LIMITING
──────────────────────────────────────────────
  • Toutes les vues d'écriture publique (adhésion, inscription, contact) :
      permission_classes = [AllowAny]
      throttle_scope = 'public'          → 20 requêtes / heure / IP (base.py)
  • Champ honeypot invisible (CSS) dans les formulaires — tout robot qui le
    remplit est automatiquement rejeté par validate_honeypot()
  • Vérification Google reCAPTCHA v3 côté serveur (score minimal 0.5) sur les
    3 formulaires publics, via un champ `recaptcha_token` supplémentaire
    validé dans `validate()` du serializer (appel à l'API Google avec
    RECAPTCHA_SECRET_KEY)
  • Les vues de lecture (événements publics, galerie) restent AllowAny mais
    throttlées à un niveau plus permissif ('public-read': 120/hour)

  @admin.register(DemandeAdhesion)
  class DemandeAdhesionAdmin(admin.ModelAdmin):
      list_display = ['nom', 'prenom', 'email', 'statut', 'dateDemande']
      list_filter = ['statut']
      actions = ['valider_et_creer_membre', 'rejeter']

      @admin.action(description="Valider et créer le Membre correspondant")
      def valider_et_creer_membre(self, request, queryset):
          for demande in queryset.filter(statut='EN_ATTENTE'):
              statut_defaut = Statut.objects.get(libelle='Nouveau converti')
              membre = Membre.objects.create(
                  nom=demande.nom, prenom=demande.prenom, email=demande.email,
                  telephone=demande.telephone, statut=statut_defaut)
              demande.statut = 'VALIDEE'
              demande.membre_cree = membre
              demande.traite_par = request.user
              demande.save()

  @admin.register(MessageContact)
  class MessageContactAdmin(admin.ModelAdmin):
      list_display = ['nom', 'sujet', 'dateEnvoi', 'traite']
      list_filter = ['traite']
      actions = ['marquer_traite']

  1. Accueil (/)
       Héro plein écran (image/vidéo), présentation courte de l'organisation,
       aperçu des 3 prochains événements publics (GET /public/evenements/),
       aperçu de la galerie (3-6 photos), témoignages, appel à l'adhésion.

  2. À propos (/a-propos)
       Mission, valeurs, historique, équipe/responsables mis en avant
       (contenu statique ou géré en CMS léger — hors périmètre API).

  3. Événements (/evenements)
       Liste filtrable (à venir / passés), recherche par mot-clé, lieu ;
       consomme GET /public/evenements/?search=&lieu=&ordering=date ;
       chaque carte affiche titre, lieu, date/heure, image, places restantes.

  4. Détail événement (/evenements/:id)
       GET /public/evenements/{id}/ — description complète, informations
       pratiques, FormulaireInscription (POST /public/evenements/{id}/
       inscription/), nombre de places restantes si capacité définie,
       désactivation automatique du formulaire si complet.

  5. Galerie (/galerie)
       GET /public/galerie/ — grille de photos, filtrable par événement,
       visionneuse plein écran (ImageViewer).

  6. Adhésion (/adhesion)
       FormulaireAdhesion → POST /public/adhesion/ (+ honeypot + reCAPTCHA) ;
       message de confirmation "Votre demande sera examinée par notre équipe".

  7. Contact (/contact)
       ContactForm → POST /public/contact/ (+ honeypot + reCAPTCHA), carte de
       localisation (Carte.jsx), coordonnées, réseaux sociaux.

  8. Mentions légales / Confidentialité
       Pages statiques (texte juridique, politique de traitement des données
       collectées via les formulaires publics — RGPD/loi locale applicable).

  9. Espace membre (/espace-membre/...)
       Connexion (réutilise /auth/login/ du back-end, restreint aux comptes
       Utilisateur liés à un Membre), Mot de passe oublié, Mon Profil
       (GET/PATCH /membre/mon-profil/), Mes Inscriptions
       (GET /membre/mes-inscriptions/) — voir PARTIE IV.K.

  10. 404 (*) — NotFound.jsx

J. FORMULAIRES PUBLICS & PROTECTION ANTI-SPAM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Les 3 formulaires publics (Adhésion, Inscription à un événement, Contact)
partagent la même stratégie de protection :

  1. Validation front (react-hook-form + zod ou yup) : champs requis, format
     email/téléphone, longueur minimale du message.
  2. Champ Honeypot.jsx : input caché via CSS (jamais display:none, plutôt
     positionné hors écran) que seul un bot renseignera → rejeté côté back
     (validate_honeypot, PARTIE IV.B.3).
  3. Google reCAPTCHA v3 (invisible) : génère un `recaptcha_token` envoyé
     avec chaque soumission, vérifié côté serveur (score ≥ 0.5).
  4. Throttling serveur : 20 requêtes/heure/IP sur les endpoints d'écriture
     publics (scope 'public', PARTIE II.K).
  5. Message de confirmation clair après soumission + email de confirmation
     automatique au visiteur (inscription à un événement) via Celery.

K. ESPACE MEMBRE (MINI-PORTAIL AUTHENTIFIÉ)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CONDITIONS D'ACCÈS :
  Un visiteur ne peut se connecter à l'espace membre QUE s'il possède déjà
  un compte Utilisateur créé par le personnel (back-office) ET lié à sa
  fiche Membre (Utilisateur.membre — cardinalité 0..1 du diagramme). Le
  site vitrine ne permet PAS l'auto-inscription d'un compte : seule la
  DemandeAdhesion (PARTIE IV.B.1) déclenche, après validation, la création
  d'un Membre — la création éventuelle d'un compte Utilisateur associé
  reste une action manuelle du Secrétaire/Administrateur dans le back-office.

FONCTIONNALITÉS :
  • Connexion (réutilise POST /auth/login/, mêmes tokens JWT que le
    back-office, mais stockage isolé dans le store de la vitrine)
  • Mon Profil : consultation et mise à jour des coordonnées personnelles
    (téléphone, adresse, email) via GET/PATCH /membre/mon-profil/
  • Mes Inscriptions : historique des événements auxquels le membre s'est
    inscrit via le site vitrine (GET /membre/mes-inscriptions/)
  • Déconnexion : invalide le token côté client (le cookie refresh httpOnly
    expire naturellement après 7 jours ou peut être révoqué côté back)

SÉCURITÉ :
  • Un Membre connecté ne peut voir/modifier QUE ses propres données
    (get_object() de MonProfilMembreView restreint à request.user.membre)
  • Aucun droit d'écriture sur les données métier (Statut, HistoriqueStatut,
    Fonction) depuis l'espace membre — lecture seule et coordonnées propres
    uniquement
