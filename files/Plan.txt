0.2 CONSTAT : UN SITE STATIQUE À TRANSFORMER EN PLATEFORME DYNAMIQUE
──────────────────────────────────────────────────────────────────────
Toutes les données actuelles (classement, statistiques, calendrier,
articles, joueurs expatriés, galerie) sont codées EN DUR dans le HTML.
Chaque mise à jour (un nouveau score, un nouvel article, un transfert)
exige aujourd'hui de modifier manuellement le code source. Ce plan
transforme ce site en une véritable plateforme média avec :
  • une base de données (PostgreSQL) qui centralise tout le contenu ;
  • un back-office (React) permettant à l'équipe rédactionnelle de publier
    des articles, saisir des résultats de matchs, gérer les joueurs, la
    galerie et les transferts sans toucher au code ;
  • un site public (React) qui reproduit fidèlement les pages, sections et
    la charte graphique du site fourni, mais dont CHAQUE section est
    alimentée dynamiquement par l'API plutôt que codée en dur.

0.3 OBJECTIFS DU NOUVEAU SYSTÈME
──────────────────────────────────
  1. Permettre à la rédaction de publier des actualités (avec brouillon,
     relecture, publication) sans intervention technique.
  2. Centraliser les données du Championnat National (clubs, classement,
     calendrier, statistiques joueurs) et les mettre à jour automatiquement
     à partir des résultats de matchs saisis.
  3. Maintenir une base "Joueurs" (sélection nationale, expatriés,
     légendes historiques) réutilisable dans tout le site.
  4. Suivre les transferts et la carrière des joueurs haïtiens expatriés.
  5. Gérer une galerie photo par album/évènement.
  6. Capturer les messages de contact et les abonnements newsletter.
  7. Offrir un site public rapide, référencé (SEO), accessible et fidèle
     à la charte graphique déjà validée (rouge/bleu du drapeau haïtien).

0.4 PRINCIPE D'AUTOMATISATION (FAÇON SITE OFFICIEL DE FÉDÉRATION / FIFA)
──────────────────────────────────────────────────────────────────────────
Comme sur un site officiel de compétition, la rédaction ne doit remplir
qu'une seule fois l'information de base ; le reste se calcule seul :

  • La rédaction saisit UNIQUEMENT le résultat d'un match (score final +
    la liste des buteurs avec la minute du but).
  → Un signal Django recalcule AUTOMATIQUEMENT :
      - le classement du championnat (points, victoires, nuls, défaites,
        buts pour/contre, différence de buts) pour les deux clubs ;
      - les statistiques individuelles (buts, passes décisives, cartons,
        clean sheets) et donc les classements "Meilleur Buteur", "Meilleur
        Passeur", "Meilleure Défense", etc. ;
      - le statut du match (À venir → En cours → Terminé) et son affichage
        dans le calendrier et sur la page d'accueil.
  • Un match "En cours" peut être rafraîchi en direct (score live) par
    l'équipe de rédaction via un simple champ "score en direct" ; le site
    public interroge l'API toutes les 30 secondes (polling) pendant les
    jours de match, avec une option d'évolution vers Django Channels
    (WebSocket) pour un vrai direct sans rafraîchissement (voir PARTIE
    II.I pour le détail technique des deux approches).
  • Les "Chiffres Clés" de la page Actualités (ex. nombre de sélections,
    de buts inscrits, de victoires de la saison) sont calculés par une
    tâche Celery périodique plutôt que saisis à la main, pour rester
    toujours exacts.

A. STACK TECHNIQUE
───────────────────
  Back-End  : Django 4.2 + Django REST Framework + SimpleJWT
  Front-End : 2 SPA distinctes servies séparément
                1) React 18 + Vite (Back-Office Rédaction)   — PARTIE III
                2) React 18 + Vite (Site Vitrine Public)     — PARTIE IV
              Router v6 + TanStack Query + Zustand (les deux projets)
  Base de données : PostgreSQL 15
  Cache           : Redis 7 (cache classement/stats + broker Celery)
  Tâches async    : Celery + django-celery-beat (recalcul stats, chiffres
                    clés, newsletters, notifications)
  Éditeur riche   : django-ckeditor (ou Tiptap côté front) pour le contenu
                    des articles
  Images          : Pillow + django-imagekit (miniatures automatiques pour
                    la galerie et les images "à la une")
  PDF             : ReportLab (génération du calendrier téléchargeable)
  Emails          : SMTP (production) / console (dev)
  Documentation API : drf-spectacular (Swagger / OpenAPI)
  Anti-spam       : Honeypot + Google reCAPTCHA v3 + throttling DRF
                    (formulaires publics)
  Live (option avancée) : Django Channels + Redis (scores en direct par
                    WebSocket) — voir PARTIE II.I
  CI/CD           : GitHub Actions
  Conteneurisation: Docker + docker-compose

B. RÔLES DE LA RÉDACTION
─────────────────────────
  Personnel interne (Back-Office, authentifié) — hiérarchie cumulative :
    REDACTEUR         → Rédige des articles (statut BROUILLON), saisit les
                         résultats de matchs et statistiques, gère la
                         galerie, consulte les messages de contact
    EDITEUR_EN_CHEF    → Tous les droits de REDACTEUR + Publie/dépublie les
                         articles de tous les rédacteurs, gère les clubs,
                         compétitions, joueurs, expatriés, transferts,
                         traite les messages de contact et la newsletter
    ADMINISTRATEUR     → Tous les droits d'EDITEUR_EN_CHEF + Gère les
                         comptes utilisateurs de la rédaction, les
                         partenaires, les paramètres généraux du site

  Public (Site Vitrine, entièrement anonyme) :
    VISITEUR ANONYME  → Consulte toutes les pages publiques, s'abonne à la
                         newsletter, envoie un message de contact.
                         (Le site n'a volontairement AUCUN espace membre :
                         il s'agit d'un site d'actualités, pas d'un espace
                         communautaire — cohérent avec le site fourni qui
                         ne propose aucune connexion visiteur.)

  class ArticleViewSet(ModelViewSet):
      # «Rédiger un article»       → create()             (REDACTEUR+)
      # «Modifier un article»      → update()/partial_update()
      # «Publier un article»       → action publier()      (EDITEUR_EN_CHEF+)
      # «Consulter un article»     → retrieve() (incrémente compteur_vues)
      # «Rechercher un article»    → list() avec ?search=
      filter_backends = [DjangoFilterBackend, SearchFilter, OrderingFilter]
      search_fields = ['titre', 'chapo', 'contenu']
      filterset_fields = ['categorie', 'tags', 'statut', 'a_la_une']

      def get_permissions(self):
          if self.action in ('publier', 'destroy'):
              return [IsEditeurOuPlus()]
          return [IsRedacteurOuPlus()]

      def get_queryset(self):
          qs = super().get_queryset()
          # Un simple REDACTEUR ne voit que ses propres brouillons
          if self.request.user.role_redaction.nomRole == 'REDACTEUR':
              return qs.filter(Q(statut='PUBLIE') | Q(auteur=self.request.user))
          return qs

      @action(detail=True, methods=['post'])
      def publier(self, request, pk):
          article = self.get_object()
          article.statut = 'PUBLIE'
          article.date_publication = timezone.now()
          article.save()
          return Response(ArticleDetailSerializer(article).data)

  class MatchViewSet(ModelViewSet):
      # «Créer un match»           → create()               (REDACTEUR+)
      # «Modifier un match»        → update()/partial_update()
      # «Consulter un match»       → retrieve()/list()
      filter_backends = [DjangoFilterBackend, OrderingFilter]
      filterset_fields = ['competition', 'club_domicile', 'club_exterieur', 'statut']
      ordering_fields = ['date_heure']

      @action(detail=True, methods=['post'])
      def saisir_resultat(self, request, pk):
          """ «Saisir le résultat d'un match» — déclenche l'automatisation
              complète (classement + statistiques, voir PARTIE II.I) """
          match = self.get_object()
          serializer = MatchResultatSerializer(match, data=request.data, partial=True)
          serializer.is_valid(raise_exception=True)
          serializer.save(statut='TERMINE')
          # le signal post_save(Match) prend le relais automatiquement
          return Response(MatchDetailSerializer(match).data)

      @action(detail=True, methods=['patch'])
      def mettre_a_jour_score_direct(self, request, pk):
          """ «Mettre à jour un score en direct» — statut EN_COURS,
              diffuse le score via Django Channels (PARTIE II.I) """
          match = self.get_object()
          match.score_domicile = request.data.get('score_domicile')
          match.score_exterieur = request.data.get('score_exterieur')
          match.statut = 'EN_COURS'
          match.save()
          diffuser_score_live(match)          # envoi WebSocket au groupe
          return Response(MatchDetailSerializer(match).data)

G. AUTHENTIFICATION JWT & SÉCURITÉ
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

STRATÉGIE JWT :
  • Access Token   : 15 minutes, envoyé dans le corps JSON
  • Refresh Token  : 7 jours, stocké en httpOnly cookie sécurisé
  • USERNAME_FIELD = 'identifiant'
  • Seul le personnel de la rédaction possède un compte — le site vitrine
    n'a aucune authentification visiteur (cohérent avec le site fourni)

FLUX D'AUTHENTIFICATION :
  1. POST /auth/login/  { identifiant, password } → { access, user } + cookie refresh
  2. React (back-office) stocke 'access' en mémoire (Zustand, jamais localStorage)
  3. Axios interceptor ajoute Authorization: Bearer <access>
  4. À expiration → POST /auth/token/refresh/ (cookie envoyé automatiquement)
  5. Mise à jour de dernier_acces à chaque login

  class LoginView(TokenObtainPairView):
      def post(self, request, *args, **kwargs):
          response = super().post(request, *args, **kwargs)
          refresh = response.data.pop('refresh')
          response.set_cookie('refresh_token', refresh, httponly=True,
                               secure=True, samesite='Lax', max_age=7*24*3600)
          user = Utilisateur.objects.get(identifiant=request.data['identifiant'])
          user.dernier_acces = timezone.now()
          user.save(update_fields=['dernier_acces'])
          response.data['user'] = UtilisateurSerializer(user).data
          return response

I.1 RECALCUL AUTOMATIQUE DU CLASSEMENT
────────────────────────────────────────
  competitions/services/classement.py :
    def recalculer_classement(match):
        """ Appelé par le signal post_save(Match) quand statut='TERMINE'
            et que les scores sont renseignés. Recrée entièrement la ligne
            de classement des 2 clubs pour cette compétition à partir de
            TOUS les matchs terminés (source de vérité unique, pas
            d'incrémentation fragile). """
        for club in [match.club_domicile, match.club_exterieur]:
            if club is None:
                continue
            matchs = Match.objects.filter(
                Q(club_domicile=club) | Q(club_exterieur=club),
                competition=match.competition, statut='TERMINE')
            victoires = nuls = defaites = bp = bc = 0
            for m in matchs:
                domicile = (m.club_domicile_id == club.id)
                bp += m.score_domicile if domicile else m.score_exterieur
                bc += m.score_exterieur if domicile else m.score_domicile
                if m.score_domicile == m.score_exterieur:
                    nuls += 1
                elif (m.score_domicile > m.score_exterieur) == domicile:
                    victoires += 1
                else:
                    defaites += 1
            ClassementLigne.objects.update_or_create(
                competition=match.competition, club=club,
                defaults=dict(matchs_joues=matchs.count(), victoires=victoires,
                    nuls=nuls, defaites=defaites, buts_pour=bp, buts_contre=bc,
                    points=victoires * 3 + nuls))

    def recalculer_stats_joueur(match):
        """ Agrège les ButeurMatch de tous les matchs terminés de la
            compétition pour reconstruire StatistiqueJoueur — alimente
            directement les classements "Meilleur Buteur", "Meilleur
            Passeur", "Meilleure Défense/Attaque/Milieu/Gardien" affichés
            sur la page Championnat. """
        joueurs_concernes = {b.joueur for b in match.buteurs.all()}
        for joueur in joueurs_concernes:
            buts = ButeurMatch.objects.filter(
                joueur=joueur, match__competition=match.competition,
                type_but__in=['BUT', 'PENALTY']).count()
            StatistiqueJoueur.objects.update_or_create(
                joueur=joueur, competition=match.competition,
                defaults=dict(buts=buts))
        # passes décisives, cartons et clean sheets suivent la même
        # logique via des modèles complémentaires (PasseDecisive,
        # CartonMatch) saisis en même temps que le résultat du match.

src/api/axiosClient.js :
  const api = axios.create({
      baseURL: import.meta.env.VITE_API_URL,
      withCredentials: true,
  });

  api.interceptors.request.use((config) => {
      const token = useAuthStore.getState().accessToken;
      if (token) config.headers.Authorization = `Bearer ${token}`;
      return config;
  });

  api.interceptors.response.use(
      (res) => res,
      async (error) => {
          if (error.response?.status === 401) {
              const { data } = await api.post('/auth/token/refresh/');
              useAuthStore.getState().setAccessToken(data.access);
              return api(error.config);
          }
          return Promise.reject(error);
      }
  );

  # actualites/views.py (section publique)
  class ArticlePublicListView(ListAPIView):
      queryset = Article.objects.filter(statut='PUBLIE').order_by('-date_publication')
      serializer_class = ArticlePublicListSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public-read'
      filter_backends = [DjangoFilterBackend, SearchFilter, OrderingFilter]
      search_fields = ['titre', 'chapo']
      filterset_fields = ['categorie', 'tags', 'a_la_une']

  class ArticlePublicDetailView(RetrieveAPIView):
      queryset = Article.objects.filter(statut='PUBLIE')
      serializer_class = ArticlePublicDetailSerializer
      lookup_field = 'slug'
      permission_classes = [AllowAny]
      throttle_scope = 'public-read'

      def retrieve(self, request, *args, **kwargs):
          instance = self.get_object()
          Article.objects.filter(pk=instance.pk).update(
              compteur_vues=F('compteur_vues') + 1)
          return super().retrieve(request, *args, **kwargs)

  # competitions/views.py (section publique)
  class ClassementPublicView(ListAPIView):
      serializer_class = ClassementLigneSerializer
      permission_classes = [AllowAny]
      throttle_scope = 'public-read'
      def get_queryset(self):
          return ClassementLigne.objects.filter(
              competition_id=self.kwargs['competition_id'])

      filterset_fields = ['competition', 'statut']

B.5 PERMISSIONS, ANTI-SPAM ET RATE-LIMITING
──────────────────────────────────────────────
  • Toutes les vues d'écriture publique (contact, newsletter) :
      permission_classes = [AllowAny]
      throttle_scope = 'public'          → 20 requêtes / heure / IP
  • Champ honeypot invisible (CSS) — tout robot qui le remplit est
    automatiquement rejeté
  • Vérification Google reCAPTCHA v3 côté serveur (score minimal 0.5) sur
    le formulaire de contact
  • Les vues de lecture (articles, matchs, classement, galerie, chiffres
    clés...) restent AllowAny mais throttlées à un niveau plus permissif
    ('public-read': 300/hour, car interrogées fréquemment par le polling
    des scores en direct)

     newsletter avec lien de désabonnement, accusé de réception du
     message de contact) via Celery.

RÉCAPITULATIF GLOBAL DU PROJET
================================================================================

  ── BACK-END ────────────────────────────────────────────────────────────
  Applications Django      : 8 apps (core, comptes, actualites, joueurs,
                              competitions, expatries, galerie, vitrine)
  Modèles                  : 21 modèles métier + 4 modèles vitrine = 25
  Serializers DRF          : 21 back-office + 4 publics dédiés + serializers
                              publics allégés dans chaque app = ~30
  Vues API (ViewSets)      : 17 principales back-office + 16 publiques = 33
  URL patterns API         : 32 back-office + 16 vitrine + 1 WebSocket = 49
  Signals                  : 3 back-office + 2 vitrine = 5
  Tâches Celery            : 6 back-office + 2 vitrine = 8
  Commandes management     : 2
  Automatisation clé        : recalcul classement + statistiques joueurs
                              (signal Match), chiffres clés (Celery beat),
                              score en direct (polling + Channels),
                              PDF calendrier (Celery)

  ── FRONT-END ───────────────────────────────────────────────────────────
  Projets React               : 2 (globeinfosport-redaction / back-office,
                                    globeinfosport-vitrine / site public)
  Pages React                  : 17 (back-office) + 10 (vitrine) = 27
  Composants réutilisables     : 30 (back-office) + 43 (vitrine) = 73
  Layouts                       : 2 (back-office) + 1 (vitrine) = 3
  Zustand stores/slices          : 3 (back-office) + 1 (vitrine) = 4
  Custom hooks                    : 8 fichiers (back-office) + 8 (vitrine) = 16
  Modules API/services axios       : 9 (back-office) + 9 (vitrine) = 18
  Groupes de routes protégées       : 2 (back-office, rôles cumulatifs) ;
                                       aucun côté vitrine (site 100% public)

  ── INFRASTRUCTURE ──────────────────────────────────────────────────────
  Base de données          : PostgreSQL 15
  Cache / Broker / Channel layer : Redis 7
  Conteneurs Docker          : 7 services (dev) + Nginx en prod
  Temps réel                  : Django Channels (WebSocket, scores en direct)
  Génération de documents      : ReportLab (PDF calendrier) via Celery
  Documentation API              : drf-spectacular (OpenAPI / Swagger)
  Anti-spam vitrine                : Honeypot + reCAPTCHA v3 + throttling DRF

  ── FIDÉLITÉ AU SITE EXISTANT FOURNI ────────────────────────────────────
  ✓ 6 pages HTML fournies → 10 pages React dynamiques (les 6 + Galerie
    dédiée + détail article + mentions légales/confidentialité)
  ✓ Charte graphique (couleurs, police, animations, icônes) intégralement
    reprise dans tailwind.config.js et les composants React
  ✓ Chaque section codée en dur dans le HTML fourni (classement, joueurs
    emblématiques, légendes, actualités, calendrier, expatriés, galerie,
    contact) devient une section alimentée par un endpoint /public/... dédié
  ✓ Automatisation ajoutée par rapport au site fourni : classement et
    statistiques recalculés automatiquement à la saisie d'un résultat de
    match, chiffres clés toujours exacts, score en direct pendant les
    matchs — un niveau d'automatisation comparable à un site officiel de
    fédération sportive
